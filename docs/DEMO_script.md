# MAHALO demo script — a day in the life of a team

A top-to-bottom walkthrough: **Executive → Product Manager → Developer → Product Manager** (closing the loop). It shows one AI agent reasoning across Jira, Confluence, ServiceNow and **real GitHub (Gitea)** at once, building charts on the dashboard, and — new — vetting its own generated code with an **independent second model** before a human approves the write.

- **Mahalo UI:** https://dw28e5je2s7b9.cloudfront.net
- **Gitea (proof of real writes):** https://d3ec76atxiij9a.cloudfront.net/ (`mahalo_admin`)
- **Logins:** Executive `exec`/`exec123` · Product Manager `pm`/`pm123` · Developer `dev`/`dev123`
- Full login/identity detail: see `DEMO-LOGINS.md`.

> All prompts below are grounded in the actual seeded demo data, so they won't return "not found" on stage. The agent is an LLM, so exact wording of answers (and which chart type it picks when unspecified) may vary slightly — that's expected.

## Opening line (set the frame)

> "Mahalo is one AI agent that reasons across Jira, Confluence, ServiceNow, and real GitHub at the same time — and it now vets its own generated code with an *independent* second model before a human approves anything. Let me walk you through a day in the life of a team, top to bottom."

---

## 1. Executive — the wide view
**Log in as `exec` / `exec123`** (the agent acts as David Kim).

1. Open the **Dashboard** — the cross-project view renders.
2. Build a chart: **"Show story points completed per project this sprint as a bar chart."**
3. Build a different chart type: **"Show delivery risk by project as a pie chart."**
4. Ask: **"What's our delivery risk across all five projects this sprint?"**
5. Ask: **"Which projects have open incidents in ServiceNow right now?"**
6. **Log out.**

*Talking point:* the exec never opens Jira or ServiceNow directly — the agent blends sprint health, git activity and incidents into one answer.

---

## 2. Product Manager — who's doing what
**Log in as `pm` / `pm123`** (the agent acts as Marcus Chen).

1. Ask: **"Give me a status summary across all my projects — sprint progress, open PRs, and incidents."**
2. Ask: **"Who is working on what in the payment project right now?"**
3. Check a specific story: **"What's the status of PAY-105, and is there a pull request for it?"**
   *(PAY-105 = Google Pay integration, in progress, has a real Gitea PR.)*
4. Open **MahaloJira** (Connections → "Open MahaloJira") — show the **Current Sprint** board and the **Backlog** tab.
5. Build a chart: **"Show open stories by assignee in the payment project as a horizontal bar chart."**
6. **Log out.**

*Talking point:* the PM sees the whole team's work plus live git activity in one place.

---

## 3. Developer — the hero flow (code + independent review + git + Jira)
**Log in as `dev` / `dev123`** (the agent acts as Lava Dev).

1. **Set up the trust story first.** Go to **Settings** and pick the **code-review model** (Nova Lite).
   *Say:* "Code is generated by Sonnet, but reviewed by a *different* model — Nova Lite — so it's genuinely independent, not the model grading its own work." *(Note: the Security-review dropdown is intentionally disabled — that's the next slice.)*
2. Ask: **"What's assigned to me right now?"** → returns **PAY-109 (Cryptocurrency payment option)** and **PAY-110 (Fraud detection enhancement)**.
3. **The hero prompt — code + independent review in one turn:**
   **"Write the code for PAY-109, the cryptocurrency payment option, and commit it to the payment-service repo on a new branch."**
   - Watch the **stage progress**: *"Generating with Sonnet 4.5… → Reviewing with Nova Lite…"*
   - See the **trust line** on the answer: *"Generated by Sonnet 4.5, reviewed by Nova Lite"* plus the review findings.
   - An **approval card** appears for the commit → **Approve it.**
4. Update Jira: **"Move PAY-109 to in progress."** → approval card → **Approve.**
5. Build a chart: **"Show my assigned stories by status as a pie chart."**
6. **Log out.**

*Talking point (the money moment):* the agent wrote code, a **second independent model reviewed it**, and the **human approved** before anything touched git or Jira.

**Then prove it's real:** open Gitea (`mahalo_admin` at the Gitea URL) and show the branch/commit you just approved is actually there.

---

## 4. Product Manager again — close the loop
**Log back in as `pm` / `pm123`.**

1. Ask: **"What progress has been made on the payment project today?"** → picks up PAY-109 now in progress with its new branch/commit.
2. Ask: **"Show me the latest pull requests and commits for payment-service."** → the developer's just-approved work shows up.

*Closing line:* "The PM sees the developer's work land in real time — Jira updated, code in real git — all through one agent, with an independent review in the loop."

## Live-demo safety tips

- **Warm it up.** The first agent call after idle can take ~40–60s (cold start). Send one throwaway prompt a few minutes before you start so the live run is snappy.
- **Check Gitea is up** before the demo — it can auto-stop on weekends. It must answer at `GET https://d3ec76atxiij9a.cloudfront.net/api/v1/version`. (Confirmed up — v1.27.3 — at script-writing time.)
- **Hard-refresh** the Mahalo UI (Ctrl+Shift+R) once before starting to clear any cached bundle.
- **Don't want to create a real branch?** You can **reject** the approval card instead of approving — the stage progress, the review, and the trust line still show; you just won't land anything in Gitea.
- **PAY-109 / PAY-110** are the Developer persona's real stories, so "what's assigned to me" and the build prompt line up exactly. PAY-105 (Google Pay) is the in-progress story with a real PR for the PM status check.
- **Optimistic progress caveat:** the "Reviewing with…" text is client-side optimistic between send and response, so on a slow turn it may appear a moment early. The final rendered "generated by X, reviewed by Y" labels are the real ones from the response.
- **Single Gitea admin by design:** every git write is owned by `mahalo_admin`; the author *name* in each PR/commit title is the correct persona. Mention it if anyone asks why the Gitea user is always the same.
