# Multi-LLM per SDLC activity — Requirements (First Slice)

## Summary

Today a single fixed Bedrock model (Claude Sonnet 4.5) performs every SDLC
activity the agent handles — code generation, review, and any security
reasoning. When the agent reports "I reviewed the code and it looks sound," the
same model is effectively grading its own output, so the review carries no
independent weight. A live test confirmed the current single-model agent is
honest (it refuses to claim it switched models and admits it has no dedicated
review or security tool), so this work is an **enhancement that adds genuine,
independent vetting** — not a fix for a dishonest agent.

This feature lets an operator choose **different Bedrock models per activity** so
that generated code is reviewed by a *different* model, and surfaces that fact to
the user ("Generated by X, reviewed by Y"). The trust story is the point; the
exact model-to-activity mapping is secondary and configurable.

The agreed **first slice** (this document) is deliberately small:

1. A Settings page with model dropdowns, persisted per persona.
2. **One** independent LLM **code-review** stage running on a *different* model.
3. Visible per-stage progress in the chat UI (not a frozen spinner).
4. A "who-did-what" trust line in the chat response.

The security-review stage, the chat "suggest-and-confirm" selection flow, and any
real static-analysis tooling are **out of scope** for this slice (see Out of
Scope). The human-in-the-loop (HITL) write gate is **unchanged**: review runs
read-only, and git/Jira/ServiceNow writes still pause for approval exactly as
today.

## Functional Requirements

### Model configuration (Settings)

- FR-1. The Settings page shall present **three** model dropdowns labelled
  **Code generation**, **Code review**, and **Security**, each populated from a
  fixed server-sanctioned allow-list of Bedrock models.
- FR-2. Each dropdown option shall show a human-friendly label (e.g. "Nova Lite
  (fast, low-cost)") rather than the raw model id.
- FR-3. The selected configuration shall be **persisted per persona** (the three
  demo personas: `pm`, `dev`, `exec`) and survive reloads and new chat sessions.
- FR-4. The **Code review** dropdown shall offer at least one model that is
  cheaper than, and distinct from, the code-generation default, so the
  independence claim is real.
- FR-5. The **Security** dropdown shall be present and persisted, but is **not
  wired to any execution stage in this slice** (reserved for a later slice). It
  shall carry a visible "coming soon / not yet active" affordance so the demo
  does not imply a working security stage.
- FR-6. The settings configuration shall be the **single source of truth** for
  model selection. The chat shall not offer a competing selection mechanism in
  this slice.
- FR-7. When no configuration has been saved for a persona, the system shall
  apply documented defaults (code-gen = current Sonnet 4.5; review = the cheap
  cross-vendor default) without requiring a prior save.

### Independent code-review stage

- FR-8. When the agent produces code as part of answering a chat turn, a
  **second, independent review model** (the persona's configured review model)
  shall review that generated code. The code to review is taken from the fenced
  code blocks of a completed reply, or from the file contents of a
  `github_commit_files` write proposal when the turn ends by proposing a write.
  When review runs on a write-proposal turn, it runs **before** the proposal is
  surfaced but does not gate it (the human approval is unchanged).
- FR-9. The review stage shall run **read-only**: it shall have **no write
  tools**, shall not create branches/commits/PRs/stories/incidents, and shall
  not interact with the HITL approval gate.
- FR-10. The configured review model id shall flow from the Settings config, to
  the thin API, to the Runtime invocation, to the review stage, without the
  operator editing environment variables or redeploying.
- FR-11. If the configured review model id is not on the server allow-list, the
  Runtime shall fall back to the default review model and record that a fallback
  occurred (the turn must still succeed).
- FR-12. The code-generation activity shall continue to use the configured
  code-generation model (default unchanged: Sonnet 4.5), preserving today's
  behaviour when no configuration is changed.

### Progress + trust reporting

- FR-13. The chat response shall carry a **structured list of stages** executed
  for the turn, each with: a stage name (e.g. `generate`, `review`), the model
  used (label + id), and a status.
- FR-14. The chat UI shall render per-stage progress ("Generating with X →
  Reviewing with Y") in place of the single frozen spinner, so the user sees the
  activity is progressing rather than stalled.
- FR-15. The chat response shall carry a **who-did-what summary** the UI renders
  as a trust line, e.g. "Generated by Claude Sonnet 4.5, reviewed by Nova Lite."
- FR-16. When the review stage produces findings, the chat response shall carry
  those findings (text) so the UI can display them alongside the trust line.
- FR-17. A chat turn that does **not** generate code shall behave exactly as it
  does today (no review stage, no trust line, existing response shape intact).

### Compatibility

- FR-18. The existing HITL propose→approve flow (`/chat`, `/chat/approve`,
  `ChatResponse`, `ActionResult`, the six gated writes) shall continue to work
  unchanged, including the branch→commit→PR chain breadcrumbs.
- FR-19. All new response fields shall be **additive and optional** so an older
  client that ignores them keeps working.

## Non-Functional Requirements

- NFR-1. **Trust/credibility:** the review stage must use a model whose id is
  verifiably *different* from the code-gen model, and that difference must be
  visible to the user. An identical gen/review model selection shall be
  surfaced as such (the UI should not imply independence that is not there).
- NFR-2. **Cost:** review defaults to a low-cost model; the demo explicitly
  accepts cheaper models.
- NFR-3. **Latency:** added latency from a second model call is accepted **only
  if** per-stage progress is visible (FR-14). The review stage must not make the
  UI appear frozen.
- NFR-4. **Offline-safety:** importing any agent/thin-API module must remain
  possible with no AWS credentials or network (matching the existing codebase
  invariant); model construction stays lazy.
- NFR-5. **Least privilege:** any new review model requires a corresponding
  `bedrock:InvokeModel` grant scoped to that model's inference-profile ARN on
  the Runtime execution role; no broader grant.
- NFR-6. **Security posture unchanged:** the thin-API Function URL stays
  `AuthType=NONE` (demo posture, already accepted); no new secrets reach the
  browser; the model allow-list is server-enforced so a hostile client cannot
  make the Runtime invoke an arbitrary model.

## Acceptance Criteria

1. The Settings page shows three dropdowns (Code generation, Code review,
   Security), each populated only from the allow-list, with friendly labels.
2. Saving a configuration for the `dev` persona and reloading the page shows the
   saved values; switching to `pm` shows that persona's own (or default) values.
3. The Security dropdown is visibly marked "not yet active" and selecting a value
   there changes no execution behaviour in this slice.
4. With review set to a model different from code-gen, sending a chat prompt that
   asks the agent to generate code yields a response whose structured `stages`
   array contains a `generate` stage and a `review` stage with the two **distinct**
   model ids. The review stage runs whenever code is present for the turn — either
   as a fenced code block in a completed reply, or as the file contents of a
   `github_commit_files` write proposal.
5. The chat UI, during that turn, shows progressing stage text (e.g. "Generating
   with … → Reviewing with …") rather than only the static three-dot spinner.
6. The completed response renders a trust line of the form "Generated by
   &lt;model&gt;, reviewed by &lt;model&gt;", and any review findings are shown.
7. A chat prompt that does **not** produce code returns with no `review` stage and
   renders exactly as it does today (no trust line, no regression).
8. The review stage never proposes or performs a write: a prompt that generates
   code and then asks to commit it still pauses at the existing HITL approval card
   for the write, and only after approval is anything written.
9. Setting review to a model id **not** on the allow-list results in a successful
   turn that used the default review model, with the fallback recorded.
10. The existing branch→commit→PR approval chain still completes end-to-end
    unchanged (breadcrumbs honoured, no re-proposal of approved steps). The review
    stage appears only on the `commit_files` step of that chain (which carries the
    file contents); the `create_branch` and `open_pull_request` steps carry no file
    bodies and therefore emit no review stage.
11. `import agent.runtime_app`, `import agent.strands_agent`, and the thin-API
    app import all succeed with no AWS credentials present (offline-safe).
12. The Runtime execution role has an `InvokeModel` grant for each allow-listed
    review model's inference-profile ARN and no broader Bedrock grant.

## Out of Scope

- The **security-review stage** execution (dropdown is persisted but inert this
  slice).
- Chat **suggest-and-confirm** model selection (explicitly deferred as harder;
  Settings is the single source of truth).
- Any **real static-analysis** tool (Semgrep/CodeQL/etc.) — LLM review only.
- **True live streaming** of tokens/stages (SSE/WebSocket) from the Runtime to
  the browser; this slice uses a structured stages array rendered with optimistic
  client-side progress (see the design, question D).
- Per-user (as opposed to per-persona) configuration; multi-tenant auth.
- Changing the HITL write gate, the six gated write tools, or the approval UX.
- Model cost dashboards / usage metering.

## Assumptions

- A-1. The three existing personas (`pm`/`dev`/`exec`) are the configuration
  scope; "per persona" means keyed on the canonical persona id already used by
  the dashboard store and `X-Mahalo-Persona` mapping.
- A-2. "Generated code" is detected from the agent turn's output (the design
  defines the concrete trigger). Turns with no code skip the review stage.
- A-3. The allow-list is small and curated by engineers from models verified
  invocable in the target account/region; it is not dynamically enumerated at
  runtime in the browser.
- A-4. Cheaper demo models are acceptable for review quality; the goal is a
  credible *independent* second opinion, not maximal review accuracy.
